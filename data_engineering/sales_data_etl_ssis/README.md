# Sales Data ETL SSIS

## Overview

**Sales_Data_ETL_SSIS** is a sales-data ETL pipeline built on SQL Server Integration Services (SSIS). The package extracts a sales CSV, validates and type-converts the rows, redirects bad rows to an error log, and loads the clean rows into a SQL Server database. A Python reference ETL is checked in alongside the SSIS package so the validation logic can be verified end-to-end on any machine (Mac, Linux, CI) without a SQL Server toolchain.

## Key Features

- **Data Extraction**: CSV source with explicit column typing in the Flat File Connection Manager.
- **Data Transformation**: `Convert_SalesDataTypes` task performs string -> DateTime + numeric conversions; the Python reference ETL applies the identical conversions.
- **Error Handling**: SSIS error-redirect routes bad rows to `dbo.SalesData_ErrorLog`; the Python reference ETL writes the same structure to the same table name in SQLite.
- **Row Count Logging**: SSIS RowCount transformation captures success counts; the SQL schema includes `dbo.SalesData_RunLog` for per-run totals (rows read / written / rejected / duration ms).
- **Automated Execution**: A SQL Server Agent job that executes the deployed SSIS package nightly is checked in as an idempotent setup script.
- **Performance**: Batch inserts into the destination; the schema includes indexes on `OrderDate` and `CustomerID` for downstream analytics.
- **Portable Verification**: A Python reference implementation makes the project's transform/validation logic auditable and unit-testable outside the SQL Server stack.

## Architecture

The SSIS project remains the production deliverable. Around it, the repo now contains the missing scaffolding: SQL DDL, SQL Agent job script, a richer data generator, a portable Python reference ETL, and unit tests.

```
SalesDataETL.dtsx                       SSIS package (production)
sales_data_etl_ssis.dtproj              SSIS project
Project.params
create_sales_data.py                    Sample data generator (clean + bad rows)
sql/
  01_create_database.sql                Idempotent DDL: SalesDataDB + tables
  02_create_sql_agent_job.sql           Idempotent SQL Agent job creation
python_reference_etl/
  sales_etl.py                          Python implementation -> SQLite default
  test_sales_etl.py                     Unit tests for transform + load
README.md / README_new.md
```

## Example Usage

After running the SSIS package (or the Python reference), the following operations are executed:

- **Extract**: Data is extracted from `sales_data.csv`.
- **Transform**: Data is converted, validated, and cleaned (`Convert_SalesDataTypes`).
- **Load**: The transformed data is loaded into `dbo.SalesData` in `SalesDataDB`.
- **Error Handling**: Rows that fail transformation (bad date, negative quantity, unparseable price) are routed to `dbo.SalesData_ErrorLog`.
- **Run Logging**: Per-run totals (rows read, written, rejected, duration) are appended to `dbo.SalesData_RunLog`.

## Getting Started

### Prerequisites

- **Production path**: SQL Server, SQL Server Management Studio, SQL Server Integration Services (SSIS), and Visual Studio with SSDT for editing the package.
- **Portable path**: Python 3.10+ (stdlib only — no external pip dependencies for the SQLite target).

### Installation

Clone the repository and navigate into the project directory:

```bash
git clone https://github.com/lmdixon23/my_dev_projects.git
cd my_dev_projects/data_engineering/sales_data_etl_ssis
```

### Running

**Production path (SQL Server + SSIS)**:

```bash
# 1. Generate sample data with a mix of clean and intentionally bad rows
python create_sales_data.py --rows 500

# 2. Create the database, target table, error log, and run log
sqlcmd -S <server> -E -i sql/01_create_database.sql

# 3. Deploy SalesDataETL.dtsx to SSISDB via SSDT/Visual Studio.

# 4. Create the nightly SQL Server Agent job
sqlcmd -S <server> -E -i sql/02_create_sql_agent_job.sql
```

**Portable verification path (Python + SQLite)**:

```bash
python create_sales_data.py --rows 500
python python_reference_etl/sales_etl.py \
    --source sales_data.csv --target sqlite:///salesdatadb.sqlite
```

### Testing

```bash
python -m unittest python_reference_etl/test_sales_etl.py
```

## Technical Specifications

- **Tool**: SQL Server Integration Services (SSIS)
- **Source**: CSV file (`sales_data.csv`, generated by `create_sales_data.py`)
- **Destination**: SQL Server database (`SalesDataDB`)
- **Tables**: `dbo.SalesData` (data), `dbo.SalesData_ErrorLog` (rejected rows), `dbo.SalesData_RunLog` (per-run totals)
- **Error Handling**: Redirected error rows + ErrorLog table
- **Automation**: SQL Server Agent (`sql/02_create_sql_agent_job.sql`)
- **Portable Verification**: Python 3.10+ stdlib-only reference ETL targeting SQLite
- **Test Coverage**: 4 tests (3 transform-validation unit, 1 SQLite integration)

## Scope

- The SSIS package still embeds the source path in the Flat File Connection Manager. The clean fix (parameterize via SSISDB at execute-time) is best made in SSDT rather than by editing `.dtsx` XML by hand; this is called out so it doesn't surprise a reviewer.
- The Python reference ETL implements only the SQLite backend. The `mssql+pyodbc://` target is accepted at the CLI but stubbed with `NotImplementedError` (see `sales_etl.py`), so the intent is visible without requiring a SQL Server to test against.
- The Python reference *is* covered by CI (`.github/workflows/ci.yml` runs `python -m unittest discover python_reference_etl`). There is no CI for the SSIS `.dtsx` package itself — that requires SQL Server + SSDT (Windows), which GitHub's Linux runners don't provide.

## Future Enhancements

1. **Parameterize the Source Path**: Move the file path into an SSIS project parameter (via SSISDB at execute-time) so the package is portable across environments. The top Scope gap; best made in SSDT, not by hand-editing `.dtsx` XML.
2. **Implement + CI-test the `mssql+pyodbc://` target**: Replace the `NotImplementedError` stub in `sales_etl.py` with a real SQLAlchemy load, and exercise it in CI against a containerized SQL Server (GitHub Actions `services:` mssql). Turns the documented-but-stubbed second backend into a tested one. (The SQLite path is already CI-covered.)
3. **Additional Data Validations**: Sales-amount sanity checks, customer-id foreign-key validation against a customers table.
4. **Data Enrichment**: Join in product/customer reference data during transform.
5. **Scaling for Larger Datasets**: Add partitioning + parallelism in the data flow — after a perf baseline shows the current flow is actually a bottleneck.
